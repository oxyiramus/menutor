# Доверие к прокси

На Linux хостовый Nginx завершает TLS и соединяется с `127.0.0.1:8080`.
Внутренний Nginx принимает HTTP и передаёт запросы в Uvicorn по Docker-сети.
Для стандартного rootful Docker с bridge и IPv4 ожидаемый TCP-адрес отправителя
внутри frontend — шлюз `172.29.103.1`. Локальный процесс может выглядеть для
контейнера так же, поэтому для доверия требуется и ключ хостового прокси.
Uvicorn доверяет только адресу frontend `172.29.103.3`.

## Подготовка деплоя

1. Убедитесь, что подсеть `172.29.103.0/24` свободна. При конфликте согласованно
   обновите подсеть, шлюз и адрес frontend в Compose, а также оба упоминания
   шлюза в настройках доверия. Подключение к сети Docker ограничьте доверенными
   службами.
2. До запуска Compose создайте ключ и два закрытых файла с одинаковым ключом.
   Выполните команды из каталога развёртывания с правами на запись в указанные
   каталоги. Мастер-процесс хостового Nginx и Docker должны иметь доступ к своим
   файлам. Существующие ключи обновляйте согласованно на обоих переходах.

   ```sh
   umask 077
   mkdir -p /etc/nginx/menutor
   proxy_key=$(openssl rand -hex 32)
   printf 'proxy_set_header X-Menutor-Proxy-Key "%s";\n' "$proxy_key" > /etc/nginx/menutor/proxy-key.conf
   printf '"172.29.103.1:%s" 1;\n' "$proxy_key" > .config/proxy-trust.conf
   unset proxy_key
   ```

3. Установите [пример виртуального хоста](host-nginx.conf.example) в конфигурацию
   хостового Nginx. Укажите домен и существующие файлы сертификата. Выполните
   `nginx -t` перед перезагрузкой конфигурации. Виртуальный хост перезаписывает
   ключ, схему и IP клиента и удаляет входящие `Forwarded` и `X-Forwarded-For`.
4. Поднимите Compose по инструкции проекта. Ожидаемый ответ для локального
   healthcheck можно проверить командой `curl -fsS http://127.0.0.1:8080/api/ping`.
   Порт Uvicorn не публикуется. Проверка здоровья backend выполняется внутри
   контейнера по порту 8000.

Внутренний Nginx строит forwarded-заголовки заново. При совпадении IP и ключа
он берёт клиентский IP из `X-Real-IP` и принимает только схемы `http` и
`https`. Для остальных запросов он использует IP и схему TCP-соединения.
Перед пересылкой в backend ключ удаляется.

## Проверка адреса и регрессия

На отдельном локальном Linux-хосте со стандартным Docker выполните
`sh tests/proxy/run.sh`. Понадобятся Docker Compose, OpenSSL, свободная подсеть
`172.29.103.0/24` и свободные локальные порты 18080, 18081 и 18443.
Тестовый Nginx использует сеть хоста и тот же шаблон виртуального хоста.
Скрипт генерирует сертификат и ключ. База и аккаунты не нужны.
Диагностический endpoint подключается только на стенде. Ожидаемый вывод:

```text
HTTPS через Nginx хоста: https 127.0.0.1
HTTP через Nginx хоста: http 127.0.0.1
Прямой HTTP с хоста: http 172.29.103.1
Прямой HTTP в Nginx: http 172.29.103.4
Прямой HTTP в Uvicorn: http 172.29.103.4
```

Прямой запрос с хоста проверяет адрес шлюза, наблюдаемый в контейнере.
Если результат отличается, проверьте режим Docker и источник TCP-соединения
на локальном стенде перед настройкой доверия. Например, на интерфейсе bridge
фильтр `tcpdump -ni <bridge> 'dst host 172.29.103.3 and tcp dst port 80'`
покажет IP источника. Для проверки достаточно заголовков пакетов, без вывода
HTTP-данных с ключом. Не расширяйте список доверия на всю подсеть.

С установленными зависимостями backend выполните
`python tests/proxy/check_uvicorn.py`. CLI Docker Compose нужен для чтения
конфигурации, доступ к демону не требуется. Ожидаются `Ran 2 tests` и `OK`.
