## Акторы, активы и потоки

- Анонимный клиент, вошедшие аккаунты A и B, браузер и потребитель экспортов, оператор деплоя и его CI-runner. Семейный участник — данные аккаунта. В перечисленных роутерах отдельная административная авторизация не обнаружена.
- Активы — email, ник, хеш пароля, access/refresh и ключ подписи, семейные записи и предпочтения, меню, рецепты, цены, категории и списки покупок, экспортированные файлы, целостность БД, доступность API, доверенный адрес клиента, учётные данные деплоя и контейнерного registry.
- Запрос браузера или произвольного HTTP-клиента проходит host Nginx → frontend Nginx → Uvicorn/FastAPI в production-шаблоне. Dev proxy Vite использует API_URL. Проверять доверие к адресу и схеме отдельно от доверия к Bearer. Содержимое тела, query/path, заголовки, идентификаторы, файлы и значения из браузерного хранилища — недоверенный ввод.
- FastAPI валидирует схемы, `api/deps.py` открывает SQLAlchemy session на запрос, `composition/{container,_infrastructure,_auth}.py` связывает сценарии и реализации. `application/use_cases/auth.py` и `infrastructure/auth/` проверяют учётные данные и токены, репозитории users/refresh_tokens связывают состояние сессии с аккаунтом. B проверяет фактические гарантии ротации, выхода, смены пароля, конкурентных запросов и изоляции сессий.
- Связи рабочих записей проверяются в сценариях и репозиториях. Ориентиры — `repositories/{base,base_category,ownership}.py`, `database/models.py`, `database/personal_categories.py` и миграция `d4e5f6a7b8c9_personal_categories.py`. Правило для проверки: аккаунт задаётся подтверждённой серверной личностью. Категории продуктов и рецептов персональные; продукты, рецепты, семья, предпочтения, меню, типы приёмов и сохранённые покупки принадлежат аккаунту. Дочерние ингредиенты, шаги, слоты и позиции проверяются через владельца родителя и принадлежность связанных объектов. Системные типы приёмов также привязаны к аккаунту. `units` — общий справочник, заполняемый `seed_defaults` в `database/connection.py`; пользовательского маршрута записи справочника в карте нет.
- Прикладные сценарии `manage_*`, `assign_preferences`, `plan_menu`, `generate_*`, `preview_*`, `flatten_recipe_products`, `calculate_recipe_cost`, `validate_sub_recipe` и `match_recipe_preferences` обрабатывают CRUD, перенос категорий, связи, копирование, расчёты, дерево рецептов, сводку и покупки. `domain/{entities,value_objects,services,ports}` задаёт правила данных, вычислений и интерфейсы. Проверять ссылки на каждом переходе: категория, продукт, подрецепт, предпочтение, член семьи, тип приёма, слот, меню, список и его позиция. Производные ответы и агрегаты могут раскрывать данные даже без прямой выдачи записи.
- Файл → multipart → `import_limits.py` / роутер → `ImportEntities` → адаптер и session → ORM. Реестр `composition/_import_export.py` подключает JSON/CSV продуктов и рецептов, JSON меню; при экспорте также компактный JSON рецептов. Результат экспорта пересекает границу браузер → локальный просмотрщик PDF, редактор или таблица. Рассматривать обработку содержимого, частичную запись, ошибки, потребление памяти/CPU и трактовку скачанного файла.

LLM, prompt injection и проверка прав провайдера неприменимы к снимку. Поле `link` рецепта видно в форме и экспортерах как данные; серверную загрузку адреса в цепочке рецепта и файлов не выявили. C проверяет потребителей поля и браузерные сетевые обращения по фактическому коду. GitHub-ссылка в AboutPanel — навигация по явному действию. PostgreSQL, внутренний HTTP proxy, registry/реестры пакетов и инфраструктура GitHub Actions применимы соответственно к B/D и D; фактическая сеть production за рамками задачи.

Отправные значения из кода для сверки на стенде: приложение задаёт 1 МиБ и 1000 записей по умолчанию в `backend/import_limits.py`; внутренний Nginx задаёт `client_max_body_size 2m` на /api/ и отдельные зоны login/register по 5 запросов в минуту с burst 10. Production Compose объявляет PostgreSQL 18.3, Dockerfiles используют Python 3.14-slim, Node 25.8-alpine и nginx:alpine. Эти настройки зафиксированы статически; фактические ответы и версии развёрнутых образов подлежат отдельной проверке.

### Инструкции для отдельного стенда

1. Из корня репозитория выделить пустой временный каталог на доступной для записи файловой системе. Поместить в него только отслеживаемый снимок: `git archive d3322adaebb1a06561e2cd3177adde40c5a561df | tar -x -C "$audit_dir"`. Проверить, что в копии отсутствует `.config/.env`. Для процессов использовать чистое окружение с нужным PATH, отдельным рабочим каталогом и без переменных рабочего приложения.
2. При наличии Python 3.14 с venv/pip и источника пакетов выполнить в копии `python3 -m venv .venv`, `.venv/bin/python -m pip install '.[dev]'`, `.venv/bin/python -m pip freeze`. Для frontend использовать `npm --prefix frontend ci` с локальным кэшем или разрешённым реестром и `npm --prefix frontend ls --all`. Записать версии, включая драйвер БД и образы; Python manifest задаёт диапазоны и сам по себе не фиксирует итоговый набор. Перед запуском отдельных существующих наборов прочитать fixtures и scripts, особенно выбор БД, Docker и сети. Для Vitest с локальными зависимостями использовать `npm --prefix frontend test`, для `tests/frontend` сверить отдельный runner; команды lint в manifest запускают автоисправление и исключены.
3. В копии задать `DATABASE_URL="sqlite:///$audit_dir/audit.sqlite"` (audit_dir — абсолютный путь), `JWT_SECRET_KEY` с отдельным случайным значением из `openssl rand -hex 32` и `CORS_ALLOWED_ORIGINS=`. Не логировать ключ и токены.
